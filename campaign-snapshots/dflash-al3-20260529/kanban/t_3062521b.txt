# T11: Training-prompt replay through inference path — does runtime AL match training per-pos when prompts are identical?

## USER HYPOTHESIS (must be tested first)

If we feed the exact training-distribution prompts (or even a held-out slice of the training data) through the dflash_llama inference pipeline, **runtime per-position accuracy should match training-side per-position accuracy**. Measured T16 runtime AL=1.363 vs training-side AL_LO=1.77 and AL_HI=2.93 with per-pos=[0.483, 0.351, 0.273, 0.233, 0.218, 0.195, 0.179]. The runtime gap should NOT exist if input distribution and weights match. This task isolates which of these is the real cause:

1. **Harness bug**: T16's report shows `per_position_accept=[0,0,0,0,0,0,0]` with AL>1 — the harness might not be counting per-position acceptance correctly. AL=1.363 might be a different (wrong) accounting path.
2. **Prompt distribution mismatch**: T16 used Alpaca-style diverse prompts; training was iq4_v17 NAS pool. Distribution shift can collapse argmax-match acceptance heavily.
3. **Hidden-state pipeline mismatch**: training uses pre-computed FP8 verifier hidden states from NAS traces (with explicit scale tensors); inference uses live verifier hidden states. Subtle quant / layout / scale differences could matter.
4. **Verifier mismatch**: training-time verifier_meta_v11 vs runtime MiniMax-M2.7-UD-IQ4_XS GGUF — vocab/tokenizer/layer-output divergence.
5. **Sampling drift**: AR vs DFlash modes may use different temperature / top-k defaults in the harness.
6. **Resume-corruption confound (background)**: step 2500 was exported by the bug-trainer; weights ARE partially fresh-init. Training-side per-pos was measured BEFORE the broken-resume happened on that ckpt path. (T1 is fixing this independently — your job is to find out what gap remains AFTER assuming weights are correct.)
