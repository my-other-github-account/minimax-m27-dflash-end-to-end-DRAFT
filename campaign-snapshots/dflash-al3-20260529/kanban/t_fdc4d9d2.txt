# T32: Eliminate NasFS as DataLoader I/O bottleneck — pre-warm cache, then launch training

## Context (USER 2026-05-28 21:00 PDT)
"A 1B param drafter model will absolutely fit on a 128GB unified memory spark. If it doesn't, you've done something very very wrong."

This is correct. The drafter is 626M params × 2 bytes (BF16) = 1.25 GB. Optimizer state (AdamW m+v fp32) = 5 GB. Activations at locked shape = small single-digit GB. Total working set should be well under 30 GB on a 128 GB unified-memory box. **There is NO legitimate memory-pressure path to a host wedge here.**

Prior root-cause hypotheses both wrong:
- ❌ "GB10 unified-memory wedge from flex_attention scores materialization" (T24 BLOCK_FOR_HARDWARE) — shape doesn't fill 128 GB.
- ❌ "TE 2.16 nightly bug" (this chat session's mid-turn diagnosis) — spark-3 with TE 2.14.1 also hit a NasFS Errno 5 at step 38.

The **actual common factor** across all failure modes (spark-2 host wedge during T24 + T31; spark-3 Errno 5 during T3-on-spark-3):
- DataLoader uses random shuffled access to ~200K `.safetensors` hidden-state files stored on the NAS at `/volume1/dnola/traces/by_hash` (2.6 TB total).
- Files are accessed via NasFS = FUSE filesystem backed by `ssh nas 'cat <path> | zstd -1 -c'` per fetch.
- NasFS cache is local (`/home/dnola/nasfs-cache` on `/dev/nvme0n1p2`, sized 800 GB).
- Under random training access, NasFS cache misses pin dataloader threads in D-state waiting on SSH-to-NAS reads. SSH tunnel saturates, NAS chokes, FUSE buffers accumulate, journald flushes caches, eventually kernel watchdog trips → host wedge OR userspace gets Errno 5.

**The fix: eliminate NasFS from the training I/O hot path.** Two paths, in order of preference:

## Phase 1 (preferred) — pre-warm the NasFS cache to cover one full epoch

NasFS has a cache. If the cache is WARM (every file the dataloader will touch has already been pulled and is locally on NVMe), there are no FUSE-to-SSH fetches during training, and the failure mode disappears.

1. Confirm NasFS mount and cache dir on spark-2:
   ```bash
   ssh spark-2 'mount | grep NasFS; df -h /home/dnola/nasfs-cache; ls /home/dnola/nasfs-cache/ | wc -l'
   ```
2. Enumerate the files the dataloader will touch one epoch:
   ```bash
   ssh spark-2 'find /home/dnola/iq4_full_run/iq4_v17_consolidated/hidden_states_nas -type l 2>/dev/null | wc -l'
   # Expect ~198486
   ```
3. Sequential read every file to force NasFS to pull and cache it. Use `xargs -P 8` to parallelize across 8 SSH workers (NasFS limits per-channel, but multiple workers each open their own SSH multiplex):
   ```bash
   ssh spark-2 'find /home/dnola/iq4_full_run/iq4_v17_consolidated/hidden_states_nas -type l | shuf | xargs -P 8 -I {} dd if={} of=/dev/null bs=1M 2>/dev/null'
   ```
4. After warming, verify cache hit count and size:
   ```bash
   ssh spark-2 'du -sh /home/dnola/nasfs-cache; ls /home/dnola/nasfs-cache | wc -l'
   ```
5. If cache size > 800 GB allocation: NasFS will evict during epoch. Two responses:
   - (a) Bump cache-bytes to e.g. 3 TB (spark-2 has 1.2 TB available — check first, this may need spark-2 disk reclamation per the macos-host-disk-reclamation pattern but for Linux).
   - (b) Repeat the warm every N steps as a background loop in a separate tmux session.
6. Once warm, launch T31's training. If failures stop occurring, this is the fix.

## Phase 2 (fallback) — full local copy to NVMe

If Phase 1 cache warm doesn't fit OR training still fails:

1. Stage actual files (not FUSE symlinks) to local NVMe:
   ```bash
   ssh spark-2 'mkdir -p /home/dnola/iq4_full_run/iq4_v17_consolidated/hidden_states_LOCAL'
   ssh spark-2 'find /home/dnola/iq4_full_run/iq4_v17_consolidated/hidden_states_nas -type l -name "*.safetensors" | xargs -P 16 -I {} sh -c "cp -L {} /home/dnola/iq4_full_run/iq4_v17_consolidated/hidden_states_LOCAL/$(basename {})"'
   ```
2. Measure total size; if > NVMe available, fall back to Phase 3.
3. Edit launcher's `HS_PATH` env to point at `hidden_states_LOCAL` instead of `hidden_states_nas`.
4. Launch.

## Phase 3 (deeper fix) — convert to sharded sequential format

If the random-access dataset shape is fundamentally too big for local NVMe, use webdataset / `.tar` shards that the dataloader streams sequentially. This is bigger surgery; only pursue if Phase 1 + 2 fail.
